## Observations

All five MUST assertions pass and the one SHOULD that was exercised passes; SHOULD 6 is n/a because its condition (a variant that reasons before answering) never fired, and the output says so deliberately rather than by omission.

The invariant the case cares about (assertion 2) is exercised hard rather than name-checked. Three distinct rungs are assigned across three variants, the original is scored at rung 1 and rung 1 is explicitly denied the status of enforcement on this class, and the enforcement decision is defended with class-specific measurement rather than vocabulary. The one place a lazy pass could have hidden is variant C, whose prompt is short enough that a reader might take "Return only this JSON" as the compliance mechanism; the output forecloses that reading ("Rung 3 required; do not ship C at rung 1 or 2", "Without grammar support C should not ship; use B").

Assertion 3 held on inspection of the prompt bodies themselves, not just on the presence of the phrase "beside the prompt". None of A, B or C contains a retry or self-validation instruction, which is the specific defect the scoring note warns about.

Two things worth flagging to the harness owner, neither a scoring problem here. First, the run was a dry run: "No user is reachable in this run, so the question the command would put through AskUserQuestion is printed here instead, and nothing is applied. No file was modified." That leaves the pole-selection and application path unexercised, but no assertion in this case tests it. Second, the output volunteers content no assertion covers (a nine-row diagnostic scorecard, a fine-tuning ceiling note, a prompt-injection analysis of the `{{EMAIL}}` interpolation). I did not credit any of it toward an assertion; it is noted only because a future assertion added here should be checked against a run where that surface exists, since it makes near-miss vocabulary easy to find.

I did not read the component under test, plugins/, docs/ or .peer-review/. Every score above is from the run output and the case file alone.

## Assertion quality

Assertion 4 is the weakest as written and two careful readers could split on it. "survive byte-identical" does not say what the unit is: the label literals, or the schema line as a whole. Here all three variants reformat the schema (A uses `"refund" | "cancel"` with spaces, B and C use `"refund"|"cancel"` without, C strips whitespace entirely) while the label strings themselves are unchanged, so a reader taking the line as the unit would score it fail and a reader taking the literals as the unit passes it. I scored the literals, since the assertion's own subject is "the fixed label sets ... and the `null` option", not the rendering. Suggest pinning it to "the four `intent` values, the three `urgency` values and the `null` option for `order_id` appear unchanged as literals". The second clause of the same assertion is currently vacuous: no variant changed a field name or label value, so "any change ... is reported as an interface change" was never tested. It happens that the response reports its other interface changes (delimiters, pinned key order), which is the behaviour the clause is reaching for, but the clause as written did not exercise it. Consider splitting that clause into its own conditional assertion, or restating it as "every interface-visible change to the template is reported as an interface change", which this run would then genuinely exercise.

Assertion 1's second half ("the recommendations are made for that class") is judged by absence rather than presence: the listed failure modes (structured-outputs parameter, prefill, effort settings) are things that must not appear, so the assertion passes on any response that simply never mentions them, including one that says nothing class-specific at all. This run passes it for the right reason (it names local serving stacks and dismisses API billing economics explicitly), but the assertion would also pass a much thinner response. A positive requirement, such as naming at least one local serving-stack mechanism, would make it harder to satisfy accidentally.

Assertions 2, 3, 5 and 7 are well formed: each names an observable artifact in the output and a specific way to fail it, and the scoring notes for 2 and 3 pre-empt exactly the near-miss readings that would otherwise have been arguable. Assertion 6 is correctly conditional and I would keep it; an unfired condition here is informative, since the reference material argues against a scaffold on this task and the run cites that reasoning rather than silently omitting one.
