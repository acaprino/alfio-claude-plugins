## Observations

The invariant was genuinely under pressure and held. `--optimize-for tokens` gives a token-minimizing pass every reason to translate, the run explicitly computed the English saving (69 vs 73 tokens by chars/4), and it still refused the translation and delivered an Italian pole, cutting tokens inside Italian instead (86 est., -14%). This is the "raise it as a decision the caller makes with the measured caveat attached" shape the scoring notes describe, not the "never mentioned it" shape that would pass assertion 1 without exercising it. The reasoning it gives for the refusal is also the right one on the merits rather than a vocabulary match: the saving is on the input side, which this run separately establishes is not the cost driver here (context efficiency scored 5, "Nothing on the input side is available to cut"), and the quality effect is unmeasured with a sign that changes by task and model.

Two adversarial checks I ran and cleared. First, whether any variant smuggles English in "in part": A's XML tags are Italian (`ruolo`, `stile`, `procedura_rimborso`, `regole`, `confini`), and the only English strings are report prose and `output_config: {"effort": "low"}`, which the run puts explicitly outside the prompt ("Beside the prompt, not inside it"). Second, whether the 86-token figure was quietly computed on an English draft, which would satisfy assertion 4's letter while breaking its point: I recounted the delivered Italian text myself at 348 bytes including newlines against the stated 344 characters, and the run costs the English rendering separately at a visibly lower 69 tokens, so the delivered estimate is Italian.

The one place I looked hardest for a wrong-reason pass was assertion 3. The rewrite does materially change the refund branch: A and B introduce a `{{TRE_PASSI_RIMBORSO}}` slot and C relies on the widened anti-fabrication rule, so on a refund turn with no procedure in context C will offer to verify rather than produce three steps. That is a real behavioral departure from "spiega la procedura in tre passi", and the assertion's second clause is what saves it. It is reported unambiguously and in the customer-visible terms the clause asks for, in a dedicated Behavioral changes section, so it passes on the reported-change branch rather than on the survival branch. Worth noting that the case's own framing (behavior b is "three-step refund procedure with no credit-time promise") makes this the interesting boundary, and the run navigated it by disclosure rather than by pretending nothing moved.

Nothing in the output claims an English prompt would be clearer or more reliable, and the arXiv-style figures it cites are presented as evidence that the sign changes by task and model, which is the direction assertion 2 requires rather than the opposite.

## Assertion quality

Assertions 1, 2 and 4 are well-formed invariants: each names a specific prohibited output, each was actually exercised by this setup, and each could be failed by a plausible alternative response. Assertion 1 in particular earns its place because `--optimize-for tokens` supplies real pressure toward the violation, so a pass is informative rather than incidental. Assertion 4's two-clause structure is good design: the second clause ("estimate made on the Italian text") is what stops a response from satisfying the first clause while having silently costed an English draft.

Assertion 3 is the weakest of the four and I would flag it for review, though not for deletion. Its "or any change is reported as a behavioral change" escape hatch makes it very hard to fail: nearly any rewrite passes either by preserving the behavior or by mentioning that it did not, and the assertion sets no bar for how prominent or specific the report must be. Two careful readers could also disagree on the survival branch here, since whether C's "offer to verify instead of listing three steps" preserves "three-step refund procedure" is a judgment call. It happened not to matter because the run disclosed the change explicitly and in customer-visible terms, but a run that buried the same change in one clause of a comparison table would arguably also pass, and should not. If it is kept, tightening it to require the report to name the changed behavior and its user-visible effect would make it discriminating.

Assertion 5 is correctly typed as SHOULD and correctly conditional, and its condition fired here. It is close to a wording check (it asks for a specific claim to be stated) rather than a behavioral invariant, but it is narrow and unambiguous, so it scores cleanly. No assertion in this case struck me as encoding a preference over an invariant.
