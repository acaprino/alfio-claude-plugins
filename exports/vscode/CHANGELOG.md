## 22.6.0

- `ibkr-trading` 2.8.0: two reports folded together, R11 on margin and risk and R14 on operations. R11 supplies the release's centre of gravity, a **Margin and liquidation** section in `account-state-and-pnl.md` built on the fact an automated system most needs and least often encodes: **there is no margin call**. IBKR monitors in real time and, below the maintenance requirement, liquidates without prior notice and without letting the account holder choose which positions, in what order, or when; a deficiency notice is best-efforts only. Entity disclosures put it more bluntly still for retail CFD and FX, and house requirements can be raised at any time without notice. Two design consequences are stated rather than implied: a risk gate must trigger with real headroom above zero excess liquidity, because at zero the decision is no longer yours, and liquidation arrives as market activity the strategy never ordered, so positions and fills can change under it without a reconciliation bug being involved.
- The risk tags gain IBKR's own definitions, with the pair most systems ignore called out: `LookAheadExcessLiquidity` and `LookAheadNextChange` show the projected state at the next margin change, which is where an intraday-comfortable position reveals that it breaches once the overnight requirement applies, while the `Full*` family reports the same portfolio "with no discounts or intraday credits" so a cushion that exists only because of them is identifiable in advance. `whatIf` margin is restated as an estimate and never a reservation, in IBKR's own words "expected" and "estimated".
- Short selling gains a section for one silent failure: availability is "indicative only and is subject to change", orders are "subject to approval by IBKR", and a short submitted without sufficient locate is **held while a locate is sought and, if none is found, expires without executing**. No rejection, no fill. The two shortability ticks are distinguished (a categorical `Shortable` score with the 2.5 and 1.5 thresholds, and tick 236 `Shortable Shares` for indicative quantity), and the settlement-time buy-in risk is recorded. Separately, `201` is sharpened in the error reference: it is a rejection but not a category, since IBKR documents it for large-size refusals as well as margin and compliance ones, so the reason string is diagnostic and the code alone must never be parsed as "insufficient margin".
- From R14, four operational corrections and additions: **Read-Only API is enabled by default** and "will block all API orders", which is a guaranteed first-deployment surprise; IBKR does not support headless operation at all, so running under `xvfb` satisfies the GUI requirement rather than removing it; the restart time is interpreted in the terminal's configured time zone rather than the host's; and `reqCurrentTime` returns terminal time synchronised to IBKR's servers by NTP, so a drift against the host clock is a signal about the host. IBC's named config keys are recorded (`AutoRestartTime`, `SecondFactorDevice`, and the 2FA retry triad), along with the reason to exercise a full restart cycle on the exact IBC and Gateway pairing: IBC 3.21.0 shipped a defect that "prevents autorestart from working with Gateway". That defect is historical and does not affect the 3.24.1 this plugin's tooling provisions, which was checked rather than assumed; the report had presented it as a current-release problem.

## 22.5.0

- `ibkr-trading` 2.7.0: the account-state research report (R9) folded in as a **new reference**, `account-state-and-pnl.md`, covering the one area the plugin had no file for: what you hold, what it is worth, and why the surfaces disagree. Five surfaces are tabulated with their documented cadences, under one organising rule: only executions are a ledger, everything else is a current-state view that overwrites itself.
- The findings that change how a system should be built: **three-minute data is not risk data**, since `reqAccountSummary` and `reqAccountUpdates` both push changed values on a cadence IBKR documents as unchangeable, so a pre-trade margin check belongs to `whatIf` and not to an account value; **`accountReady == false` is a documented staleness flag** meaning the IB server is mid-reset and its values may be wrong, which almost no integration reads; and **a second `reqAccountUpdates` silently overrides the first** with, in IBKR's words, no error message, so two components each subscribing for their own account leave one reading someone else's with nothing in the logs.
- The two PnL feeds are documented as *allowed* to disagree, which retires a whole class of debugging session: Account Window and Portfolio Window use "a different source of information and a different reset schedule", Account Window realized PnL resets to zero once a day while the Portfolio Window follows a TWS-configured, instrument-specific schedule, and account-level PnL silently requires the TWS setting "Prepare portfolio PnL data when downloading positions". The reference's rule is to name the surface in your own field names, since "realized PnL" without a stated source is a question rather than a number.
- Positions gain their keying doctrine: `(account, conId)`, with no close event at all (a partial close is a smaller quantity and flat is a zero row), `positionEnd` marking the initial snapshot only, and `reqPositions` documented as unavailable above 50 subaccounts in FA or Introducing Broker masters, where `reqPositionsMulti` replaces it.
- One correction to what 2.5.0 recorded from R6: the current-day execution limit **can** be extended to seven days by a TWS Trade Log setting, but IB Gateway cannot change Trade Log settings, so the deployment this plugin recommends is permanently limited to midnight onward. Every site that states the limit now states the Gateway caveat with it. Flex is documented as the reconciliation source with its token lifetime and master-account visibility, while its trade-to-`execId` mapping and latency are recorded as measure-before-you-depend-on-it. The audit command gains a matching Account State section, and the probe register gains the `avgCost` units question, whose answer every position-sizing calculation silently assumes.

## 22.4.8

- `ibkr-trading` 2.6.0: the advanced-order-structures report (R8) folded in, covering brackets, OCA, conditions, combos, hedges, adjustable stops and scale orders. Its headline finding contradicts advice this plugin gives elsewhere and is now stated wherever that advice appears: **binding is not free**. IBKR documents that "the process of order binding from the API cancels/resubmits an order working on an exchange", which "may affect the order's place in the exchange queue", so a clientId-0 client calling `reqOpenOrders` to gain control over resting manual orders reprices its own queue position on every one of them. `reqAllOpenOrders` is now the recommended call when the need is to see rather than to act.
- A second documented race joins the bracket file: attached-order submission needs "a small delay of 50 ms or less after placing the parent order for processing, before placing the child order. Otherwise the error '10006: Missing parent order' will be triggered." `10006` on a child is therefore a retryable staging race, not a broken bracket, and the bracket checklist says so.
- New structures documented rather than left implicit: hedging orders are the same attached mechanism under another name, with the same activation rule ("a child order is submitted only on execution of the parent") in three shapes (attached forex trade, beta hedge, pair trade) and their own refusal family (10007, 10009, 10010, 377-380, 393); adjustable stops attach to stop-family orders and, when their trigger price is penetrated, **modify the parent instead of transmitting a child**, so nothing new appears in the open-order list; scale orders are documented as "only available via TWS and the TWSAPI" with an unpublished parameter envelope whose refusal codes (408-410, 417-419, 433, 446-449) are the practical way to map it; and non-guaranteed combos are opt-in, requiring the flag set to 1 as a `TagValue("NonGuaranteed", "1")` in smart-combo routing, since native exchange spreads are guaranteed by default.
- As with R6, one of the report's OPEN items was a retrieval failure rather than an unknown: it could not source error 350, which is in the published table this plugin ships ("Minimum quantity is not supported for best combo order"), and it likewise could not reach the hedging and modification pages that answer through the documented `.md` route. The existing OCA doctrine, the per-leg combo pricing constraints and the what-if budget were re-confirmed unchanged.

It presented the disclosure block and ended its turn, which to the operator is exactly what a finished run looks like, so a run in another repository sat waiting for hours on someone who believed it had already stopped. The gate now uses the host's question mechanism, so the pause is visible as a pause.
- Consent is read as intent, not matched against a token. The gate required a literal `yes` and refused `ok`, which is a granted consent recorded as a withheld one: the failure mode that looks like caution and is not. Any plain affirmative in any language proceeds, any plain refusal stops, a reply that is neither is asked about once more rather than resolved by the implementation, and an operator who asks a question back gets an answer and the question again. Silence is still never consent, and R5 now carries the rule in harness-independent terms so a second binding inherits it.
- A transport failure on the very first call offers to resend rather than ending the run. Nothing partial exists at that point and the packet is unchanged, so the retry travels under the consent already given. The common case is a timeout while the challenger is thinking, which the socket cannot distinguish from a dead connection; the run no longer answers it by telling the operator to relaunch by hand, nor by blaming the gateway without evidence.

## 19.2.0

- Tracks marketplace 19.2.0 (`senior-review` 9.0.0, `codebase-xray` 2.2.0). The `_pipelines` bundle now enforces one rule end to end: evidence derived from a shared artifact cannot corroborate the claims in that same artifact. N reviewers agreeing on a premise they were all handed is one observation, not N. The old pipeline derived context once and then explored it with fifteen agents, which produced confident agreement about whatever the first observer got wrong.
- Every reviewer finding now declares two fields: the **load-bearing premise** (the single proposition whose falsity collapses the finding, required to be minimal, falsifiable and scoped) and its **premise_provenance** (`independent`, `shared-context` or `mixed`, recording causal dependence rather than citation). Twelve reviewer agents carry the fields in their output formats, and the `/team-review` prompt template requires them.
- New agent `review-premise-auditor` runs in a new Phase 1c, in parallel with the X-ray pass and blind to it: no `.deep-dive/` in any form, no interconnect map. It derives claims from the diff, the code and the tests, hunting specifically for multiplicity (a probe path beside a periodic one, a bootstrap path beside a steady-state one). It never compares its own output, which is what makes the blindness verifiable instead of merely asserted. Phase 1d reconciles the two derivations into `01-knowledge-provenance.md` and turns every contradiction into a `disputed` row in the map.
- The verification panel goes from three lenses to four. **Lens 0** attacks the finding's premise rather than the finding, runs first, and is gated on provenance: `independent` findings skip it. It is a veto, not a vote, because local correctness cannot outvote a refuted premise; a verifier can be entirely right that the cited line does what the finding says while the inference to the conclusion is dead because another path exists. It may only refute on a `file:line` counterexample, and a refutation targeting the PREMISE kills the finding while one targeting shared SUPPORT strikes only that leg.
- The interconnect map is relabelled in its own header as a fallible hypothesis index rather than ground truth, and every row now carries a status. A fourth value, `disputed`, means two derivations reached incompatible conclusions with both sides cited and neither resolved. `Missing` and `Disputed` are kept as separate states throughout: absence of evidence is not contradictory evidence.
- `review-logic-integrity-auditor` is rewritten from map-first to map-first-never-map-authoritative. An empty map section is now a hypothesis that lowers a category's priority rather than a fact that removes it, and the targeted hunt gained an independent-discovery step and a contradiction hunt that are not optional when the mapped anchors produce nothing.
- Consolidation weighs agreement by provenance. Findings that agree from disjoint or independent premises are **corroborated**; findings that agree from the same shared premise are an **echo**, reported as such, raising neither confidence nor severity. The context utilization rate is demoted from a quality metric to an operational one, since a high value on a wrong map is the signature of the failure this work exists to prevent.
- X-ray gains an always-on Phase 0, Project Knowledge Discovery, which runs at every depth including lite and writes `knowledge/navigation.md` and `knowledge/documentation-leads.md`. It separates two roles a document plays: as evidence it stays an unverified claim, but as a **discovery lead** it is a first-class input to collect early. Refusing to read a project's own index does not make the analysis more rigorous, it makes it blind to intent.
- **Breaking:** `/team-review`'s `--skip-interconnect` is renamed `--no-context` with no alias. The X-ray pipeline keeps its own `--skip-interconnect`, which is a different flag with a different meaning: there it skips only the interconnect map. Raw mode also now skips the new Phase 0c, because knowledge leads distributed to N reviewers would themselves be shared context.
- Two deliberate divergences from the Claude Code source, both recorded in the files that carry them. Lens 0 runs on `review-verification-lens` rather than on `review-premise-auditor`, so that the blind deriver and the fully-primed challenger are different agents and the blindness is structural rather than instruction-dependent. ## 16.2.0

First release as a VS Code extension. The catalog was previously a set of 36 `.github/` bundles you copied into each project by hand.

They are copied rather than contributed because 45 of them carry supporting files, and a contributed skill loads only its `SKILL.md` ([microsoft/vscode#304721](https://github.com/microsoft/vscode/issues/304721)).
- Commands to refresh, remove and reveal the installed skills, plus the `daodan.autoSync` and `daodan.skillsLocation` settings.
- Uninstalling removes only the skills the extension installed. A skill directory it did not create is reported and left alone.
- Fixes in the `research` bundle: `quick-searcher` and `deep-researcher` were missing `websearch` in their tool lists and so could not search the web; Claude Code tool names survived in prose; `$SKILLS` was used without being defined; and `team-research` had an empty section and a mangled step list left by the original port.

The bundles are still copyable per project for anyone who wants a narrower install.
